> 작성: 2026-11-26 · 근거: index.html 전체 코드 검토 + 오늘 시험(6·7사로, 약 13분 사격, 235발씩)의 진단 기록
> 목적: 증상마다 덧대는 수정을 멈추고, 원인을 구조 수준에서 정리한 뒤 기초부터 다시 짠다.

## 1. 지금 태블릿이 하는 일 (전체 지도)

모든 일이 **브라우저의 한 줄(메인 스레드)** 에서 차례로 실행된다. 한 일이 길어지면 나머지는 기다린다.

### 1-1. 카메라 장면마다 (1초에 약 30번, 장면 간격 33ms)
| 순서 | 하는 일 | 걸리는 시간(실측) |
|---|---|---|
| ① | 카메라 화면을 캔버스에 그려서 픽셀을 읽어 옴 (`drawImage` + `getImageData`, 400×300) | **평균 16.3~16.8ms** |
| ② | 감지 범위의 밝기 계산, 배경과 비교, 잡음 지도 갱신, 레이저 후보 판정 | 약 1ms |
| ③ | 화면 상자 크기를 재서 표적의 화면 좌표 → 분석 좌표로 변환 (`getBoundingClientRect`) | 작음(단, 화면 배치에 의존) |
| ④ | 상태 글자 갱신(감지 정보 표시 등), 처음 준비될 때 안내 문구·버튼 변경 | 작음 |
| **합계** | | **평균 17.4~17.8ms, 최대 약 30ms** (장면 간격 33ms의 절반 이상) |

→ **장면 1장 처리 시간의 94%가 "픽셀 읽어 오기"** 다. 레이저 판정 자체는 1ms 정도로 가볍다.

### 1-2. 한 발이 기록될 때
- 점수 계산(정수·소수점), 발 목록에 추가
- 맞는 순간 큰 점수 반짝임(화면 전체 덮개 애니메이션), 점수판 숫자 갱신, 과녁 위 탄착 다시 그리기(전체 발)
- 0.25초 뒤: 리그 기록 Firebase 저장, 큰 시계 판 글자 갱신(글자 길이가 바뀌면 판 크기 다시 재기)
- 마지막 발이면 0.65초 뒤 경기 종료 처리

### 1-3. 주기적으로 도는 일 (서로 따로 돌아감)
| 주기 | 하는 일 |
|---|---|
| 0.15초 | 카운트다운 숫자 갱신 |
| 0.2초 | 리그 상태 확인(시간 종료), 화면 갱신 |
| 3초 | 진단 기록 전송(&diag=1) |
| 5초 | 리그 상태 Firebase 저장(연결 표시 유지) |
| 2분 | 서버 시계 맞추기 |
| 수시 | Firebase 수신(컨트롤 타워 상태, 명령, 0점 추가 등), 화면 크기 변경 처리 |

### 1-4. 경기 시작·종료 때
- 시작: 이전 경기 지우기 → 카메라 노출·화이트밸런스·초점 **잠금 요청** → 기준 화면 다시 잡기(화면이 안정될 때까지, 최대 6초) → 카운트다운 → 0.7초 안정화 → 감지 시작
- 종료/연습 끝: 카메라 **잠금 해제 요청** → 화면 배치 원래대로 → 기록 저장

## 3. 근본 문제 (증상과 연결)

### 문제 1. 장면을 "줄 서서 받지" 않고 "그때그때 훔쳐 봄"
- 방식: 화면에 장면이 표시될 때 알림(`requestVideoFrameCallback`)을 받아, **그 순간 화면에 있는 장면**을 읽는다.
- 알림이 늦게 오거나 처리 중이면 그사이 지나간 장면은 **영원히 사라진다**. 줄에서 기다려 주지 않는다.
- **증상**: 놓친 발(한쪽 태블릿만 기록), 발 직후에 더 자주 놓침

### 문제 2. 픽셀 읽기가 무겁고, 화면 그리기·통신과 같은 줄에서 경쟁
- 장면 간격 33ms 중 **17ms를 픽셀 읽기**에 쓰고, 남은 16ms에 화면 갱신, 애니메이션, Firebase, 타이머 6종이 모두 끼어든다.
- 어느 하나가 16ms를 넘기면 다음 장면을 놓친다.
- **증상**: 건너뛴 장면, 큰 시계 판을 넣은 뒤 더 나빠짐, 한 발 직후 일이 몰리면 다음 발을 놓침

### 문제 3. 표적 위치를 "화면 좌표"로 들고 있음
- 표적은 화면(화면 상자) 기준으로 저장되고, 장면마다 **화면 배치를 재서** 분석 좌표로 바꾼다.
- 그래서 **인식이 화면 배치에 묶여 있다**. 주소창이 접히거나, 큰 시계 판으로 바뀌거나, 전체화면이 되면 인식에 영향이 간다.
- **증상**: 인식이 통째로 멈춤(감지 범위 밝기 0), 화면 배치를 바꿀 때마다 생기던 문제들

### 문제 4. 카메라 설정이 경기마다 흔들림
- 경기 시작마다 노출·화이트밸런스·초점을 잠그고, 끝날 때마다 풀어 준다. 그때마다 카메라가 다시 맞추고, 기준 화면도 다시 잡는다.
- 노출을 "어둡게 보정"만 요청하고 노출 시간은 카메라 자동에 맡긴다. 그래서 노출이 33~42ms로 길다.
- 노출이 길면 ① 장면 속도가 떨어지고 ② 방아쇠 순간 총구가 튀면 점이 **번져서 찍히고** ③ 밝은 레이저가 **하얗게 포화**된다.
- **증상**: 같은 발인데 태블릿마다 위치가 다름(MISS vs 9.4), 흰색 포화 탈락, 시작 직후 "화면 흔들림" 판정

### 문제 5. 인식과 화면·경기 진행이 한 덩어리
- 인식 코드 안에서 안내 문구, 버튼, 상태 표시를 바꾸고, 저장도 부른다. 경기 진행(수업용/리그)은 같은 함수(`startMatch`, `reset`, `finishMatch`)에 **모드 표시를 붙여** 갈라 쓴다.
- 한 곳을 고치면 다른 곳이 영향을 받는다. 리그 기능을 넣으면서 수업용 흐름에 예외 처리가 계속 늘었다.
- **증상**: 수정할 때마다 다른 데서 새 문제가 생김(까만 화면, 연습 후 본사격 등)

### 문제 6. 시간 기준이 여러 개
- 화면 시각(`performance.now`), 기기 시계(`Date.now`), 서버 추정 시각(Firebase), 직접 맞춘 서버 시각이 섞여 있고, 타이머가 6종이 따로 돈다.
- 발 시각은 "빛이 사라진 걸 확인한 순간"에 찍혀서, 실제 맞은 시각보다 0.07초 이상 늦다.
- **증상**: 동시 시작 어긋남(직접 맞춘 뒤 해결), 완료 시간이 실제보다 조금 늦게 측정

### 문제 7. 같은 조건으로 다시 시험할 방법이 없음
- 인식을 바꾸면 매번 학생·태블릿·레이저총으로 다시 쏴야 확인된다. 같은 발을 두고 "전 방식 vs 새 방식"을 비교할 수 없다.
- **증상**: 원인 추측 → 수정 → 다시 쏘기 → 다른 결과의 반복

### 참고: 피할 수 없는 부분
- **보는 각도와 해상도에 따른 위치 오차**: 두 태블릿이 같은 발을 평균 0.2~0.35점 다르게 본다. 대회에서는 사로당 태블릿 1대만 채점하므로 "두 대 차이"는 생기지 않지만, 한 발마다 ±0.2점 정도의 측정 오차는 남는다. 정면에 가깝게, 크게 찍을수록 줄어든다.

**결론**
1. 장면 수집은 **메인에서 줄을 만들어 일꾼 스레드로 넘기고**, 일꾼 스레드가 **표적 주변만 원본(I420)으로 복사**해 처리한다. 장면 손실 0, 처리 비용 1/90.
2. 인식 엔진은 RGB 대신 **밝기(Y)·색차(U·V)** 로 판정하도록 옮긴다(빨강은 V가 크게 오름). 표적 주변만 RGB로 바꿔도 비용은 작다.
3. 카메라가 실제로는 **24장/초**로 돈다. 노출을 줄이는 방법을 따로 찾아야 한다(속도↑, 번짐·흰색 포화↓).

## 3-2. 노출 시험·장면 녹화 결과 (2026-11-26, camlab.html, 6사로)

### 노출 시험
| 방법 | 장면 속도 | 밝기(가운데) |
|---|---|---|
| ① 기본(자동 노출) | 23.9장/초 | 159 |
| ② **노출 보정 최저(−2)** | **29.8장/초** | 69 |
| ③ 장면 속도 30 요구만 | 23.9 | 163 |
| ⑤ 수동 노출 10ms (ISO 100) | 29.7 | 15 (너무 어두움) |
| ⑥ 수동 노출 10ms + ISO 800 | 30.0 | 111 |
| ⑦ 수동 노출 20ms + ISO 400 | 30.0 | 111 |
| ⑧ ISO 800만 | 23.9 | 163 |

- 수동 노출은 **ISO와 함께 지정하면 적용된다**(0단계에서 "안 됨"이었던 이유: ISO 없이 지정).

### 장면 녹화 (약 2.5분, 3,532장, **빠진 장면 0**)
- 새 수집 방식(줄 세우기 + 일꾼 스레드 + 표적 주변 원본 복사)이 실제 사격 중 **장면을 하나도 잃지 않았다.**
- 레이저 빛은 **89%의 발에서 장면 딱 1장**에만 찍힌다(나머지 11%는 2장). → 장면 1장만 잃어도 그 발은 사라진다.
- 2장에 걸치는 비율(11%)로 보면 레이저가 켜지는 시간은 **약 5ms**로 추정된다.
- 점은 평균 **세로 22 × 가로 13픽셀**로 찍히고, 23%는 **세로로 2배 이상 긴 줄**(최대 세로 60픽셀 = 과녁 반지름만큼)이다. 방아쇠 순간 총이 튀는 움직임이 5ms 동안 그대로 찍힌 것이다.
- 레이저 중심은 거의 항상 **하얗게 포화**된다(62장 중 58장). 그래서 색(V)이 약하게 오르는 발도 많다(V 상승 21~39).
- 빠른 연사는 **0.42~0.6초 간격**까지 나온다.
- 녹화 시작 직후 색 변화 없이 밝기만 오른 장면 5개가 있었다(카메라가 설정에 자리 잡는 중).

### 결론 (설계에 바로 반영)
1. **장면 수집은 새 방식으로 확정**(손실 0 실측).
2. **노출을 짧게 하면 안 된다.** 레이저가 5ms밖에 안 켜져서, 노출 10ms·간격 33ms면 장면과 장면 사이 빈틈에 빛이 떨어져 **절반 이상을 놓친다.** 노출이 장면 간격만큼 길어야 빈틈이 없다.
   → **"노출 보정 최저(−2)"로 30장/초**에 맞춘다(빈틈 없이 장면 속도 24→30, 화면도 어두워져 포화 감소).
3. **번짐은 노출 시간과 상관없다**(빛이 5ms만 켜짐). 총이 튀는 움직임이 그대로 찍힌 것이다.
   → 점수 위치를 "가장 밝은 픽셀"로 잡으면 긴 줄의 어느 끝이 잡히느냐에 따라 점수가 크게 달라진다(→ MISS vs 9.4). 처음에는 **빛 덩어리 전체의 중심**으로 정했다가, 3-4의 분석으로 **줄의 시작점(아래쪽 둥근 점)**으로 바꿨다.
4. 판정은 **색(V)과 밝기(Y)를 함께** 써야 한다(포화된 발은 색이 약함).
5. **0.4초 간격 연사**도 따로 잡혀야 한다(지금 방식은 빛이 사라졌는지 확인하는 동안 다음 발을 못 받음).

## 4. 재설계안 (기초 공사)

### 4-1. 목표
1. **장면을 하나도 놓치지 않는다** (건너뛴 장면 0, 놓쳤으면 반드시 기록에 남는다)
2. **인식은 화면 배치·화면 갱신·통신과 완전히 분리**한다
3. **카메라 설정은 보정할 때 한 번 정하고 경기 내내 고정**한다
4. **같은 장면 기록으로 언제든 다시 시험**할 수 있다

### 4-2. 새 구조 (층 나누기)
```
[카메라] ──장면(시각 포함)──▶ [① 장면 수집]  ──▶ [② 인식 엔진]  ──발 사건──▶ [③ 경기 진행]  ──상태──▶ [④ 화면]
          (별도 일꾼 스레드)      줄 세워 하나씩     영상 좌표만 사용              수업용·리그 공통        한 번에 모아 그리기
                                                    화면·DOM 모름                 타이머 하나·시계 하나         ↓
                                                                                    └──────────▶ [⑤ 저장·통신] (한꺼번에, 뒤로 미뤄서)
                                  [⑥ 진단: 장면 번호 끊김·단계별 시간·판정 이유를 항상 기록]
```

| 층 | 하는 일 | 지금과 다른 점 |
|---|---|---|
| ① 장면 수집 | 카메라 장면을 **줄 세워** 받는다(`MediaStreamTrackProcessor`). **별도 일꾼 스레드(Web Worker)** 에서 표적 주변만 잘라 읽는다 | 메인 줄이 바빠도 장면이 줄에서 기다린다. 읽는 양도 화면 전체 → 표적 주변으로 줄어든다 |
| ② 인식 엔진 | 지금의 판정 규칙(배경·잡음·색·켜짐·사라짐)을 그대로 옮기되 **영상 좌표만** 쓴다. 결과는 "발 사건(장면 시각, 위치, 점수, 근거)"으로만 내보낸다 | 화면 배치와 무관. 같은 입력이면 항상 같은 결과 |
| ③ 경기 진행 | 대기 → 준비 → 카운트다운 → 사격 → 종료를 **하나의 상태 기계**로. 수업용과 리그는 "규칙 설정"만 다름 | 모드 예외 처리 제거. 시간은 서버 시각 하나로 |
| ④ 화면 | 상태가 바뀌면 다음 화면 갱신 때 **한 번에** 그린다 | 인식 중에 화면을 건드리지 않음 |
| ⑤ 저장·통신 | 모아서, 뒤로 미뤄서 보낸다 | 장면 처리와 겹치지 않음 |
| ⑥ 진단 | 카메라 장면 번호가 끊긴 곳(진짜 놓친 장면), 단계별 처리 시간, 모든 판정 이유를 늘 기록 | 지금처럼 "추정"이 아니라 "확인" |

**카메라 설정**: 보정할 때 노출 시간을 **짧게(목표 8~16ms)** 직접 정하고 고정한다(기기가 지원하면). 장면 속도 30장 보장, 번짐·흰색 포화 감소. 경기마다 잠금·해제를 반복하지 않는다.

**호환성 대책**: 장면 줄 세우기·일꾼 스레드를 지원하지 않는 기기에서는 지금 방식으로 자동 전환한다(그때도 ②~⑥ 구조는 같음).

### 4-3. 시험 방법도 함께 만든다
- **장면 녹화·재생**: 실제 사격 몇십 발의 장면(표적 주변만)을 녹화해 두고, 인식 엔진에 **그대로 다시 넣어** 결과를 비교한다. 학생 없이 PC에서 수백 번 반복 시험할 수 있다.
- **두 대 비교 시험**: 지금처럼 같은 과녁을 두 대로 찍어 발마다 맞춰 보는 분석을 표준 절차로 쓴다.
- **합격 기준(안)**: 30발 × 3회에서 놓친 발 0, 건너뛴 장면 0(또는 끊김이 기록으로 확인됨), 두 대 평균 차이 0.3점 이하, 인식 멈춤 0.

### 4-4. 진행 순서 (안)
| 단계 | 내용 | 확인 |
|---|---|---|
| 0 | **태블릿 능력 확인 페이지**: 장면 줄 세우기·일꾼 스레드 지원 여부, 실제 장면 속도, 노출 시간 직접 설정 가능 여부, 장면 읽기 시간 측정 | 태블릿에서 1분 |
| 1 | 인식 엔진 분리(규칙은 그대로, 영상 좌표 전용) + 장면 녹화·재생 시험 도구 | PC에서 녹화본으로 지금 결과와 같은지 확인 |
| 2 | 장면 수집 층(일꾼 스레드, 줄 세우기, 표적 주변만 읽기) | 건너뛴 장면 0 확인 |
| 3 | 경기 진행 상태 기계 + 화면 층 + 저장 층 (수업용·리그 공통) | 수업용·리그 모두 기존 기능 그대로 동작 |
